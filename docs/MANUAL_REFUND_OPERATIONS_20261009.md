## 운영 순서

1. 회원의 환불 요청을 홈페이지 관리자 ‘결제 · 환불 원장’에서 확인한다. 주문번호, 원 거래번호(TID), 상품과 금액을 대조한다.
2. 기존 이니시스 관리자에 로그인하여 같은 거래를 조회하고, 환불 조건을 검토한 운영자가 **전액 취소를 완료**한다. 취소 요청 중·실패 상태를 완료로 취급하지 않는다.
3. 홈페이지의 해당 환불 요청에서 원 TID, 전액 취소 금액, 실제 취소 완료 시각, 확인 근거를 입력한다. 원 거래와 대조했다는 확인란을 선택하고 ‘취소 완료 기록 반영’을 누른다. 키·카드번호·개인정보 원문을 확인 근거에 넣지 않는다.
4. 확인창을 승인하면 주문·환불·거래 원장·감사 기록과 이용 권한 회수가 하나의 DB 트랜잭션으로 저장된다. 이는 카드 취소를 새로 요청하는 버튼이 아니다.
5. 목록을 새로고침하여 전액 환불 상태, 확인자·취소 시각·근거와 권한 회수를 확인한다. 이니시스 취소 내역과 홈페이지 환불 원장을 일별로 대조한다. 두 시스템 사이에는 자동 동기화가 없으므로 PG 취소 후 홈페이지 반영을 같은 업무에서 완료한다.

부분 취소, 기존 자동 취소 처리 중/결과 불명 거래, 금액이 다른 거래는 이 화면에서 확정할 수 없다. 별도 대사 후 처리하며 전액 취소로 잘못 입력하지 않는다. 이니시스에서 아직 취소하지 않은 요청만 반려할 수 있다. PG 취소 후 홈페이지 저장이 실패하면 카드 취소를 다시 누르지 말고 원장을 새로고침한 뒤 기록 반영만 재시도한다.

## 구현과 안전장치

- `INICIS_REFUND_MODE=manual`, `INICIS_REFUNDS_ENABLED=false`를 명시한 환경에서만 동작한다. 이번 작업에서는 원격 설정을 바꾸지 않았다. 설정 누락 시 수동 반영은 차단된다.
- 관리자 인증·동일 출처·검수 읽기 전용/점검 모드를 유지한다. 결제 승인을 수동으로 만들어내는 기능은 추가하지 않았다.
- 단일 성공 이니시스 카드 승인, 원 TID 및 전액 금액, paid 주문/requested 환불, 기존 성공 환불 없음, 승인 이후의 취소 시각을 확인한다. 부분 요청을 전액으로 덮어쓰지 않는다.
- DB batch의 첫 INSERT가 주문별 유일한 취소 처리권을 확보하고 현재 상태를 다시 검증한다. 중복·경합·기존 자동 환불 claim은 전체 트랜잭션을 실패시킨다. 원장이나 감사 기록 저장 실패 시 권한 회수까지 모두 롤백한다.
- 단건 열람권과 팩에서 발급한 열람권을 제거하고 남은 크레딧을 소진한다. 해당 광고의 다른 유효 paid 주문이 있으면 그 광고 노출은 유지한다.
- `inicis_manual_refund_recorded` 이벤트에 확인자, 시각, TID, 금액, 근거를 남긴다. `verification=operator_attestation`이며 PG API로 검증한 결과라고 표시하지 않는다. 관리자 원장에서 확인 기록을 다시 읽을 수 있다.
- 자동 승인 실패 시 필요한 망취소 처리는 기존 구현을 유지한다. 일반 고객 환불을 망취소로 대체하지 않는다.
