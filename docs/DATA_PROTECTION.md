# 데이터 백업·보존·복구 운영

## 2026-09-13 병원 서류 후속 변경

병원 확인 서류는 확인 완료 시 또는 제출 후 30일에 파기한다. 만료 시 열람을 차단하고 일일 요청 기반 정리에서 삭제한다. 관리자 확인 후 R2 삭제 실패나 R2 삭제 뒤 DB 실패 모두 재시도한다. 탈퇴하면 미만료 서류도 정리하며 병원 기본정보는 회원 프로필과 분리해 원본 삭제로 공고 자동입력이 사라지지 않는다. [처리 기준·실행 한계](HOSPITAL_DOCUMENT_CONSENT_2026-09-13.md).

기준일: 2026-09-13. 최신 검증과 배포 상태는 [통합 검수](INTEGRATION_AUDIT_2026-09-13.md), 이전 운영 관측은 [관리자·저장 검수](ADMIN_STORAGE_AUDIT_2026-09-12.md)를 참고한다.

날짜·체크섬 표시, 다운로드 검증과 페이지 이동을 수정했다. 0013부터 동의 증빙을 포함한 39개 테이블을 백업한다. 아래는 최신 소스 기준이며 운영 반영 여부는 통합 검수의 배포 기록을 따른다.

## 운영 구조

- 원본 운영 데이터: OpenAI Sites D1 바인딩 `DB`
- 백업 저장소: Sites R2 바인딩 `BACKUPS`
- 자동 실행: 한국 날짜 기준 하루 첫 요청에서 보존기간 정리 후 일일 백업
- 수동 실행: 현재 관리자 화면은 조회·다운로드 전용이다. ‘지금 백업’ 버튼은 없으며 백업 POST 요청도 405로 차단된다.
- 백업 형식: `medihelpers-d1-backup-v1` JSON
- 무결성: 저장 직후 R2에서 다시 읽어 SHA-256을 재계산하고, 일치한 백업만 성공으로 기록
- 순환 보관: R2 백업 35일, 실행 이력 1년
- 제외 데이터: 로그인 세션(`auth_sessions`)은 백업하지 않음
- 범위: 지정된 39개 DB 테이블의 JSON 스냅샷. R2 업로드 이미지·서류 파일 자체의 별도 복제 백업은 포함하지 않는다.
- 구직글 원장: `job_seeker_posts`와 역할별 가입 기본값 `member_registration_profiles`를 `0012` 백업 테이블 목록에 포함

Sites 배포 버전과 GitHub는 프로그램 소스의 복구 지점이다. 회원·이력서·상담·결제 데이터는 D1/R2 백업으로 별도 보호하며, 배포 버전이 DB 백업을 대신하지 않는다.

## 자동 보존기간

| 데이터 | 처리 기준 |
|---|---|
| 만료 로그인 세션 | 만료 즉시 정리 |
| 탈퇴 후 재가입 제한용 HMAC 식별값 | 30일 |
| 종료된 상담 | 종료·최근 수정 후 3년 |
| 종료·입사 채용 건 | 원칙적으로 3년, 청구 기록이 있으면 5년 |
| 완료·취소·환불 결제 원장 | 5년 |
| 개인정보 열람·관리자 감사 로그 | 3년 |
| R2 DB 백업 | 35일 |
| 백업·보존 실행 이력 | 1년 |

법률·세무 검토에서 다른 기간이 확정되면 공개 개인정보처리방침과 서버 정리 기준을 같은 배포에서 함께 변경한다.

## 탈퇴 처리

- 로그인 자격증명과 모든 세션을 즉시 폐기한다.
- 이력서, 연결 구직글, 관심 항목, 회원 활동, 알림 설정, 동의 기록, 인재 열람권과 잔여 크레딧을 즉시 제거한다.
- 결제 기록이 없으면 계정을 삭제한다.
- 결제 기록이 있으면 이름·연락처·프로필을 비우고 최소 계정 식별자와 거래 원장만 법정 기간 동안 보관한다.
- 역할별 추가 가입정보도 삭제하고, 보존된 거래에 연결된 병원 광고는 종료한다.
- 현재 이력서와 접수 당시 지원서가 참조하지 않는 개인 사진을 정리한다. 이미 지원 병원에 제공한 제출본 사진은 해당 접수 기록의 보존기간 동안 유지한다. 스토리지 실패 시 다음 보존 실행에서 재시도한다.
- 법정 기간이 끝나면 자동 보존 작업이 거래 원장과 남은 탈퇴 계정을 제거한다.

## 개인 업로드 보존

- 활성 계정의 미참조 `profiles/` 사진은 업로드 후 7일을 초안 저장 유예로 둔다. 현재 이력서나 접수 스냅샷의 참조가 있으면 보존한다.
- `verifications/hospitals/` 서류는 원장 `retention_until`을 확인한다. 미래 시각이나 파싱 불가/미지정 기간은 임의로 지우지 않는다. 원장이 없는 파일은 7일 유예 후 정리한다.
- 병원 공개 배너 `hospitals/`는 이 개인 파일 정리의 대상이 아니다. 실패한 정리는 보존 실행 이력에 남으며 다음 실행에서 재시도한다.
- DB JSON 백업에는 파일 바이트가 없으므로 이 규칙은 파일 복원 보장을 뜻하지 않는다.

## 관리자 점검

1. `/admin` 로그인 후 `백업 · 보존 기록`을 연다.
2. 저장소가 `정상 연결`인지 확인한다.
3. 마지막 일일 백업과 보존 정리 시각이 24시간 이내인지 확인한다.
4. 최신 성공 백업에서 ‘검증 후 받기’를 사용한다. 브라우저가 파일 SHA-256과 응답 체크섬을 대조하며 불일치 시 중단한다. 목록의 ‘체크섬 기록 있음’은 메타데이터 존재이고 파일을 방금 검증했다는 뜻이 아니다.
5. 내려받은 파일은 회사가 관리하는 암호화 저장소에만 보관한다.

관리자 실행 시각은 KST로 표시한다. 자동 실행은 요청에 의존하며, 트래픽이 없으면 정해진 시각에 실행되는 구조가 아니다.

## 복구 절차

복구는 현재 운영 DB를 덮어쓸 수 있는 중요 작업이므로 웹 화면에서 자동 실행하지 않는다.

1. 장애 시점 이후 쓰기 기능과 회원가입을 임시 중단한다.
2. 관리자 콘솔에서 장애 직전 백업을 내려받는다.
3. 파일의 SHA-256을 관리자 화면·응답 헤더의 체크섬과 대조한다.
4. 별도 임시 D1에 먼저 복원하고 테이블 수·회원 수·주문 합계를 검증한다.
5. 개인정보 보호책임자와 운영 책임자가 승인한 뒤 운영 DB 복원을 수행한다.
6. 로그인 세션은 복원하지 않으므로 모든 사용자가 다시 로그인한다.
7. 복원 시각, 담당자, 원인, 검증 결과를 사고 기록에 남긴다.

목표 복구 수준은 데이터 손실 최대 24시간(RPO 24h), 복구 개시 후 4시간 이내 서비스 정상화(RTO 4h)다. 이는 보장·실측 결과가 아니다. 2026-09-12에는 합성 데이터 38개 테이블의 별도 SQLite 복원만 검증했다. 실제 D1 복원 리허설과 업로드 파일 복원 절차는 미검증이다. 실제 Cloudflare 이전 후에는 Cron Trigger와 D1 Time Travel 도입을 검토해 자동 실행 보장을 강화한다.
