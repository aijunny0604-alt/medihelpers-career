# 배포 무결성·재발 방지 규칙

## 목적

클로드 작업, Codex 작업, GitHub 소스와 Sites 운영 소스가 갈라져 수정이 누락되거나 특정 PC에서만 로그인·권한이 동작하는 문제를 방지합니다.

## 단일 기준선

- 현재 개발·배포의 유일한 기준 브랜치는 GitHub `agent/medihelpers-ui-stability`입니다.
- Sites 소스 `main`은 기준 브랜치의 검증된 배포 후보를 그대로 받는 미러입니다.
- Sites `main`, 로컬 작업 브랜치 또는 과거 배포 커밋을 새 개발 기준으로 삼지 않습니다.
- 기준 브랜치를 변경하려면 `AGENTS.md`, `docs/DEPLOY.md`, 이 문서를 같은 커밋에서 먼저 수정합니다.

## 작업 시작 게이트

다음 항목을 모두 확인하기 전에는 코드를 수정하지 않습니다.

1. GitHub와 Sites 원격을 모두 fetch합니다.
2. 기준 브랜치와 현재 작업본의 SHA 및 앞뒤 커밋 수를 확인합니다.
3. 클로드 작업 폴더의 미커밋 파일과 최근 커밋을 확인합니다.
4. 기존 사용자 변경은 보존하고 깨끗한 별도 작업본에서 통합합니다.
5. 기준 브랜치에만 존재하는 모든 커밋이 배포 후보의 조상인지 확인합니다.

## 배포 게이트

아래 조건을 모두 만족한 하나의 커밋만 배포할 수 있습니다.

- 병합 충돌 표시와 미커밋 파일이 없습니다.
- 클로드 최신 기준 브랜치가 배포 후보의 조상입니다.
- `npm test`, `npm run build`, Worker 문법 검사와 `git diff --check`가 통과합니다.
- `.openai/hosting.json`의 기존 `project_id`, D1 `DB`, R2 바인딩을 유지합니다.
- 검증된 동일 커밋을 먼저 GitHub 기준 브랜치에 반영하고, 그 SHA를 Sites `main`에 미러링합니다.
- 패키지와 Sites 버전의 `commit_sha`가 그 동일 SHA와 일치합니다.

하나라도 실패하면 배포하지 않고 원인을 해결한 뒤 전체 검증을 처음부터 다시 수행합니다. 강제 push로 우회하지 않습니다.

## 다른 PC 로그인·권한 게이트

로그인, 회원가입, 역할, 세션, 관리자 또는 캐시 관련 변경은 새 브라우저 조건으로 다음을 확인합니다.

| 사용자 | 로그인 후 필수 확인 | 기대 결과 |
|---|---|---|
| 의료인 | `/api/account`, `/api/resumes` | `role=doctor`, HTTP `200` |
| 병원 | `/api/account`, `/api/member-center` | `role=hospital`, HTTP `200` |
| 관리자 | `/api/account`, `/api/admin-console` | `isAdmin=true`, HTTP `200` |

- 반대 역할의 보호 API는 `401` 또는 `403`이어야 합니다.
- 쿠키가 차단된 환경의 같은 탭에서도 보조 세션 토큰으로 권한이 유지되어야 합니다.
- SPA HTML 응답은 `Cache-Control: no-store`여야 하며, 해시가 붙은 CSS·JavaScript만 장기 캐시합니다.
- 로컬 `devApiMock`과 QA 전환 결과를 운영 권한 검증으로 인정하지 않습니다. 반드시 실제 운영 D1과 운영 URL에서 확인합니다.

## 배포 후 게이트

1. 배포 상태가 `succeeded`인지 확인합니다.
2. 운영 URL의 HTML 캐시 헤더와 최신 해시 자산을 확인합니다.
3. 쿠키가 없는 새 세션에서 의료인·병원·관리자 권한 매트릭스를 다시 실행합니다.
4. 기준 브랜치와 배포 SHA 일치를 확인합니다.
5. 결과를 `CHANGELOG.md`, `docs/STATUS.md`, `docs/TEST.md`에 기록합니다.

이 다섯 항목이 끝나기 전에는 사용자에게 배포 완료라고 보고하지 않습니다.
