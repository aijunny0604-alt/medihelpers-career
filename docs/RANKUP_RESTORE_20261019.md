# 2026년 10월 19일 랭크업 복구 결과

사용자의 “기존 랭크업에서 사용 중이던 시스템 모두 그대로 복구” 요청에 따라 신규 개발을 중단했다. **정식 홈페이지의 랭크업 접속 복귀는 완료**, 기존 결제수단 설정은 관리자 로그인 대기 상태다. 전체 회원 인증과 실결제 완료로 표시하지 않는다.

## 실제 복구 순서

1. 기존 원본 121.254.171.115에 HTTPS로 접속해 정상 응답을 확인했다.
2. 신규 production D1을 먼저 export하고 백업 복원 무결성을 검증했다.
3. 현재 live 설정에서 가입·신규 주문을 끄고 drain 모드를 배포했다. production DB와 PG 환경·키를 유지했으며 신규 가입/주문/이력서 쓰기 차단과 기존 승인 경로 유지 관련 5검사를 통과했다.
4. 실제 서비스 상태 `drain`, `checkoutEnabled=false`를 확인한 뒤 최종 백업과 새 거래 원장 0건을 확인했다.
5. **2026-10-19 12:01:04~05 KST**, www/apex Workers Routes 2개만 해제했다. 이후 Zone의 Route 목록이 0개임을 확인했다.
6. 정식 www/apex HTTPS 200과 브라우저의 원래 랭크업 홈·회원 로그인/가입·채용목록/상세를 확인했다.
7. 전환 때 꺼둔 카드·실시간계좌이체·무통장 복구를 위해 기존 관리자 로그인 화면을 열었다. 현재 로그인 대기이며 결제수단이 공개 폼에 없는 상태를 확인했다.

DNS 레코드·NS·메일 DNS·TLS 설정은 변경하지 않았다. 기존 Cloudflare 프록시를 거쳐 랭크업 원본으로 연결된다. DNS 권한이 없어 실행서의 DNS-only 변경은 수행하지 않았고, Route 해제만으로 공개 접속 복귀를 검증했다.

## 기능 검수

- www/apex 홈과 원본 홈 본문, 아이디 로그인, 가입 구분, 개인·병원 약관, 채용 메인/전체 목록/JK 상세, 인재 목록, 커뮤니티, 고객센터, 서비스 안내, 다이렉트 폼, 관리자 로그인 화면을 읽기 검수한다.
- 브라우저에서 개인·병원 로그인 구분, 개인·병원 가입 링크, 전체 공고 목록의 기존 병원 8건, JK 상세의 모집·업무·접수 항목을 확인했다.
- 채용 메인 `employ_index.html`의 광고 구역 2곳은 “등록된 정보가 없습니다”로 표시된다. 전체 채용목록 `employ_list.html`에는 기존 공고가 표시되므로 공고 소실로 판단하지 않는다. 광고 노출 설정은 관리자 확인 대상이다.
- 로그인·가입·게시·메일·결제 제출은 하지 않았다. 실제 고객 로그인/권리와 PG 승인·취소 성공을 의미하지 않는다.

공개 경로 16개는 모두 HTTP 200·TLS 검증 성공·해당 화면 표식 확인을 통과했다. 최초 채용 메인 검사에서는 상세 링크가 있다는 가정 때문에 1건이 실패했으며, 브라우저로 광고 메인과 전체 목록을 구분한 뒤 해당 두 경로만 다시 검수했다. 원래 검사 기록도 비공개 작업 폴더에 보존했다. 공개 경로 검수 JSON과 홈 화면 PNG는 전달 폴더에 저장했다.

문서 변경 후 `npm run build`, `git diff --check`, 문서 18개의 상대 링크 417개 확인을 통과했다. 신규 앱 전체 3,102검사는 앞선 개발/배포 검수 결과이며 이번 복구 과정에서 재실행한 수가 아니다. 결제수단 재활성화와 실제 로그인/거래 검수는 아직 완료하지 않았다.

## 다음 작업자의 주의사항

- **신규 앱 재배포·Route 재연결 금지.** 신규 서비스 재개는 사용자 요청 후 별도로 진행한다.
- `medihelpers-staging`은 production DB를 사용하는 보존 환경이다. stage SQL을 덮어쓰거나 Worker/DB/기존 PG 키를 삭제하지 않는다.
- drain 배포 과정에서 Cloudflare가 Route ID를 재생성했다. 복귀 전 최초 ID로 삭제하려던 호출은 일치 검사에서 중단됐고 변경되지 않았다. 최신 Route 목록을 다시 읽은 후 패턴·스크립트·ID를 모두 확인해 실제 두 Route를 해제했다.
- 원래 결제수단은 카드/실시간계좌이체/무통장 켬, 휴대폰 끔이다. 키와 MID를 재발급하지 않고 원래 수단만 복구한다.
- 새 거래가 존재하는 다른 시점에는 이번 0건을 재사용하지 않는다. Route 제거로 새 승인 반환 경로도 구 서버로 향하므로 현재 거래 상태를 다시 확인해야 한다.
