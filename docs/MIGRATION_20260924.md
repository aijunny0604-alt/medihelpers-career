# 랭크업 → 신규 메디헬퍼스 운영 전환 준비

기준일: 2026-09-24. 기존 공개 사이트와 DNS, 신규 소스·빌드·자동검사를 조사했다. 기존 관리자/DB/이니시스 계약 화면은 아직 접근하지 않았으므로 데이터 건수·비밀번호 호환성·MID 재사용 승인은 미확정이다. 사용자 결정: 이전 가능한 자료를 검증하여 이전하고, 특히 기존 회원을 최대한 보존한다.

## 현재 판정

**준비 진행 가능 / DNS 전환 및 실결제 개시 보류.** 기존 사이트의 DNS·이니시스 키·계약·회원 데이터는 변경하지 않았다. 코드 검사 통과가 실제 PG 승인/환불 성공을 의미하지 않는다.

## 확인한 현재 상태

- 운영 예정: https://www.medihelpers.co.kr/ (www 대표 주소 제안; apex도 HTTPS 유지 후 대표 주소로 연결).
- 현재 www A: 121.254.171.115, TTL 600초.
- NS: ns1.koreafree.co.kr / ns1.whoiskorea.co.kr. 이는 DNS 제공 서버이며 도메인 등록업체·로그인 권한을 확정하는 근거는 아님.
- MX: ASPMX.daum.net(10), ALT.ASPMX.daum.net(20). SPF: v=spf1 include:_spf.daum.net ~all.
- 웹사이트 이전 시 MX·SPF·DKIM·DMARC·기존 서브도메인은 별도로 보존한다. 메일 발신 서비스 도입 시 기존 수신용 MX를 덮어쓰지 않는다.
- 기존 홈페이지와 /main/index.html HTTP 200. 랭크업 로그인·구인/구직·부동산·게시판 경로 확인. 부동산/커뮤니티는 새 제품과 일대일 대응되지 않으므로 보존·종료·별도 공개 방식을 결정해야 한다.
- 신규 사이트는 Sites 테스트 배포 377. 운영 예정 Cloudflare 타깃은 로컬 빌드 검증만 했으며 Cloudflare 계정·D1/R2·커스텀 도메인 생성/연결을 실행하지 않았다.

| 차단 | 실제 이메일 | 발신 도메인/키 미설정. 이전 회원 재설정·가입·복구 메일 실제 수신 확인 필요 |

| 확인 | 기존 링크·검색 노출 | 구 상세 URL별 매핑과 301 필요. 없는 자료를 전부 홈으로 보내지 않고 명시적 안내/410 적용 검토 |
| 확인 | 백업·복원·업로드 | 운영 D1/R2 신규 환경에서 복원 리허설 및 첨부파일 체크섬 대사 필요 |

## 회원 이전 원칙

1. SQL 전체 백업 + 첨부파일 원본 + 테이블/컬럼 설명 + 회원/권한/결제 코드표를 받는다. 파일을 Git·공개 저장소·이슈에 올리지 않는다. 제한된 저장 위치에서 원본 해시·추출 시각·건수를 기록한다.
2. 관리자 계정·탈퇴/정지 계정·중복 이메일·이메일 없는 회원을 분리한다. 정상 회원을 임의 삭제하거나 이메일만 같다고 자동 합치지 않는다. 구 관리자 등급을 새 관리자 권한으로 자동 승격하지 않는다.
3. 구 회원번호 → 새 account_id의 고정 매핑을 만들어 공고·이력서·첨부·결제 소유권을 연결한다. 재실행해도 중복 생성하지 않는 importer는 실제 스키마 수령 후 작성한다.
4. 기존 아이디가 이메일과 다르면 legacy login alias/아이디 찾기 안내 필요. 신규 사이트는 이메일 로그인이다. 기존 회원의 로그인 경험을 조용히 바꾸지 않는다.
5. 새 비밀번호는 PBKDF2-SHA256 방식이다. 구 해시 형식·salt·반복 수·문자 인코딩을 확인한다. 호환되면 제한된 이전 로그인 후 재해시하는 방식을 검토하고, 호환되지 않으면 계정을 유지한 채 본인 확인/메일 링크로 재설정한다. 평문 비밀번호 추출·공통 임시 비밀번호·해시의 잘못된 복사는 금지.
6. 이름·연락처는 원문과 정규화본 비교. 이메일 누락/중복은 별도 본인 확인 경로가 필요하다. 이 문제 때문에 회원 자체를 버리지 않는다.
7. 공개 이력서·연락처 공개·마케팅 동의는 원래 증거와 시점을 보존한다. 알 수 없는 공개 설정은 임의 공개하지 않는다. 과거 동의를 새 약관 동의로 조작하지 않는다.
8. 신규 가입 필수항목이 예전 데이터에 없어도 사용자에게 필요한 시점에 보완받는 전환 절차를 설계한다. 가입정보 수정 잠금과 충돌하지 않게 이전 회원의 검증/보완 상태를 별도로 둔다.
9. 기존 유료 공고 만료일·남은 열람 횟수·이미 열린 인재·환불 이력은 보존 대상이다. 기존 결제를 재승인하거나 청구하지 않는다. 구 TID/주문번호와 신규 주문은 출처로 구분한다.
10. 기존 이력서가 새 최소정보 기준을 못 채우면 비공개 보관+보완 안내를 검토한다. 기존 유료 권리는 별도 보존한다. 최종 공개 방식은 건수 확인 후 결정한다.

## 읽기 전용 데이터 검증 도구

실행: node scripts/migration-preflight.mjs <보호된-정규화-JSON-경로>

- 입력은 SQL이 아닌 UTF-8 JSON. 실제 랭크업 컬럼→아래 형식 변환은 원본 스키마를 받은 후 확정한다.
- schemaVersion:1, sourceCounts:{members,resumes,posts,payments,entitlements}, 각 테이블 배열 필수.
- 모든 행 legacyId:문자열. members:email,role(doctor/hospital),status(active/suspended/withdrawn),name,phone,consentEvidence.
- resumes/posts:memberId,visibility(public/private),publicationConsent. posts의 resumeId는 해당 회원 이력서를 참조.
- payments:memberId,amount(정수 원),refundedAmount,status,tid. entitlements:memberId,paymentId,remainingCredits,expiresAt(ISO 문자열 또는 null).
- 누락/중복 ID·이메일, 고아 소유권, 공개 동의, 결제/환불 금액, 권리의 원 결제 연결을 확인한다. 결과에는 테이블·행번호·문제코드만 출력하며 개인정보·비밀번호를 출력하지 않는다.
- blocker가 있으면 종료코드 2, 입력 오류는 1. 0이어도 자동 이전 승인 아님(importReady:false). 실제 DB 변경 기능 없음.
- 원본 건수 선언은 SQL에서 별도로 대사해야 한다. 선언된 건수만 맞는다고 자료가 완전하다고 판단하지 않는다. 첨부파일 실물/해시·금액 총합·날짜/인코딩·개별 동의 증거·권리 정책은 후속 별도 검증.

## 이니시스 기존 계약을 이어 쓰는 준비

기존 MID 유지가 목표이나 자동 보장은 하지 않는다. 랭크업 호스팅형 계약인지 독립 가맹점인지, 기존 PC/모바일 모듈 종류, 신규 모듈 사용 권한, 도메인(www/apex)·리턴/노티 URL·출발 IP·취소 API 이용 조건을 이니시스에 확인한다. 새 signKey 발급/교체가 구 사이트 결제에 영향을 주는지도 먼저 확인한다. 키는 채팅/소스가 아닌 운영 시크릿 저장소로 전달한다.

PC/모바일 결제 성공·취소·실패·통신 단절·중복 리턴·금액/주문/MID 불일치·승인 후 DB 장애·새로고침·환불 후 재접근·잔여권리 회수·일별 PG 원장 대사를 테스트한다. 테스트 MID 통과 후 별도 승인된 소액 실결제와 취소를 검증한다. 구 사이트 결제 TID의 환불 창구는 전환 후에도 유지한다.

## 전환 순서와 복구

1. 랭크업/도메인/PG 접근 확인 → 전체 백업 및 데이터 매핑 → 격리 환경 이전 리허설.
2. 운영 호스팅 계정에 staging D1/R2와 DNS 검증 주소 준비. production과 분리. 실제 이메일·PC/모바일 PG·복원 시험.
3. 이전 전후 회원/공고/이력서/결제 건수·금액 총합·잔여권리·파일 체크섬 일치, 누락/중복/고아 0 또는 승인된 예외명단 확인.
4. 구 URL별 리다이렉트, www/apex HTTPS, canonical/sitemap, 수신 메일 유지 확인. 중복 사이트 검색 노출 방지.
5. 오픈 시간 확정 → 구 사이트 쓰기/신규 결제 중지 → 마지막 증분 백업 → 신규 DB 반영 → 검증.
6. 전환 승인 후 웹 A/CNAME만 계획대로 변경. 현재 TTL 600초이나 DNS 캐시·인증서·네임서버 변경 효과를 별도로 확인. 구 호스팅 바로 해지하지 않는다.
7. 전환 직후 회원 로그인·비밀번호 복구·공고/이력서 소유권·결제/취소·메일·모바일 점검. 실패 시 신규 쓰기/결제를 먼저 멈추고 원장 보존 후 기존 DNS 복구. 새 결제/데이터를 버리는 단순 DNS 되돌리기는 금지.
8. 안정화와 마지막 PG 정산/환불·데이터 보존 확인 후 구 호스팅 종료.

## 외부 확인에 필요한 정보

- DNS 관리 업체와 접근 가능 여부, www/apex 현재 인증서/전체 DNS export.
- 랭크업 관리자·DB/FTP 백업 다운로드 경로, 백업 날짜, 스키마/비밀번호 방식 설명(비밀번호 원문 불필요).
- 이니시스 관리자 접근 가능 여부, 계약 유형/사용 모듈/허용 결제수단/기존 거래 환불 방법.
- 운영 Cloudflare 계정 소유자 및 운영 담당자. 기존 계약 재사용과 호스팅 선택 확정 전 DNS를 바꾸지 않는다.

## 검증 결과

기존 검사 810개 재통과(단위245 + Worker565). 신규 이전 사전검증 도구 12개 테스트 통과. Cloudflare 빌드·Worker 문법 통과, 운영 기본값 5개·대표 도메인 HTML/SEO 4경로·테스트 로그인/키 누락 결제 차단 2경로 확인. 운영 API 39응답도 확인. Cloudflare Worker 원본 1,829,891bytes / gzip 434,923bytes. 실회원/실결제 데이터로 실행하지 않음.
