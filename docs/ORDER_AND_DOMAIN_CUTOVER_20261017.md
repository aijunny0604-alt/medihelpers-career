## 기존 주문 처리 방식

신규 사이트 결제를 계속 닫는 현재 조건에서는 **구 신규 주문을 먼저 중단하고 기존 진행 거래를 정리한 뒤 웹을 전환**하는 방식이 우선 후보다. 기존 호스팅에 결제를 중계하는 상시 의존성을 새로 만들지 않는다. 아직 구 주문 중단을 실행하거나 미처리 거래가 모두 없다고 판정하지 않았다.

| 주문 분류 | 처리 원칙 |
|---|---|
| 신청만 있고 승인 근거 없음 | 신규 결제 성공·이용권으로 반입하지 않음. 미결 신청 그대로 보존하고 PG/입금 결과 확인 |
| 승인 완료 및 유효 광고/권리 | 기존 출처·주문 식별자·기간·잔여량 보존. 이미 반입한 광고와 대조하며 재청구·중복 발급 금지 |
| 입금 대기/가상계좌/처리 중 | 입금 가능 기한과 수신 경로 확인. 결과 확정 전 도메인으로 콜백을 끊지 않음 |
| 취소 완료 | PG 취소 근거와 기존 서비스 상태 대조. 새 사이트 주문인 것처럼 수동 환불 처리하지 않음 |
| 중복/누락/불명확 TID | 예외로 남기고 금액·일시·MID·원 주문을 함께 대조. 표시 TID만으로 자동 결합하지 않음 |

보호된 작업 장부에는 출처, 원 주문번호, 거래번호, 신청/승인/취소 시각, 금액, PG 결과, 광고/권리, 처리 근거, 담당자, 완료시각을 기록한다. Git에는 고객별 원문이나 거래번호를 넣지 않는다. 기존 카드 7건의 표시 TID 중 중복이 있었으므로 LEGACY_PAYMENT_IDENTIFIERS_20261017.md의 예외를 유지한다.

## 실제 전환 당일 실행 순서

1. 전환 시각과 공개 범위를 확정한다. 회원 재개/새 가입/결제는 계속 닫는지 명시하고, 문의·신청 쓰기도 허용할지 구분한다. 현재 open-without-checkout 후보는 STAGING_READ_ONLY=false이므로 모든 쓰기 차단 후보가 아니다.
2. 구 신규 주문 중단 방법을 확인·적용하고 PC/모바일/다이렉트 경로에서 새 주문 생성이 중단됐는지 확인한다. 메뉴 링크를 숨기는 것만으로 완료 처리하지 않는다. PG 키 삭제·재발급이나 구 승인/통보 수신 차단은 하지 않는다.
3. 구 진행 거래를 PG 원장과 대조한다. 미확정 거래가 남으면 전환을 대기하거나 별도로 검증된 콜백 유지안을 사용한다. 목록의 0건만으로 이 단계를 통과시키지 않는다. 정해진 시간만 기다렸다는 이유로 완료하지 않는다.
4. T0 시각의 전체 DNS export, 새 두 DB SQL, Worker 버전·설정·배포 소스 SHA, 기존 주문/권리 장부를 저장한다. 백업 SHA·무결성과 되돌릴 값을 확인한다. 이번 SQL을 전환 당일 최신 백업으로 재사용하지 않는다.
5. 기존 A와 충돌하는 www/apex Custom Domain 등록을 한 번에 검토한다. 웹 연결에 필요한 변경만 수행하고 MX/TXT/메일 CNAME, NS 및 기존 호스팅은 유지한다. 충돌 메시지를 무시하거나 zone 전체를 재가져오지 않는다.
6. 후보가 바꾸는 DB(stage→production), workers.dev(true→false), SITE_ORIGIN을 검토한 뒤 동일 검증 SHA를 배포한다. 설정 전환에는 --keep-vars를 사용해 예전 SITE_ORIGIN/차단 값을 남기지 않는다. 일반 UI 재배포 명령과 혼동하지 않는다.
7. apex/www HTTPS·인증서, 홈/공고/이전 링크, no-store, 차단 유지, 실제 관리자 접근, 메일 링크의 새 원점 및 기존 유효 광고를 확인한다. 새 실결제 시험은 별도 사용자 진행 전까지 열지 않는다.
8. 기존 거래 지연 통보/오류를 감시하고 전환 완료 시각과 예외를 기록한다. 구 호스팅은 유지한다.

이 순서의 2·3·4가 완료되기 전에는 Custom Domain 전환을 실행하지 않는다. 현재 PC hosts 수정은 하지 않았으며, 원본 접근이 필요할 때만 LEGACY_ORIGIN_ACCESS_20261011.md의 별도 관리 환경 절차를 따른다.

## 복구 시 실행 순서

1. 새 서비스 쓰기를 막고 현재 D1 변경분·주문·로그를 보존한다. 구 PG 결과를 임의로 실패/환불 처리하지 않는다.
2. 새 Worker의 www/apex Custom Domain 연결을 제거 또는 되돌리고, 확보한 원본 DNS 값으로 웹 A를 121.254.171.115 / DNS-only로 복원한다. 메일 DNS와 Cloudflare NS는 유지한다.
3. 검수 Worker는 cloudflare.rollback.json의 stage DB/검수 주소 구성으로 복원한다. **이 파일 배포만으로 DNS가 복원됐다고 간주하지 않는다.** production DB를 stage DB로 덮어쓰지 않는다.
4. 공개 DNS·HTTPS·구 관리자·기존 주문/권리 상태를 재확인한다. 새 DB 쓰기 발생분은 rollback-delta-report.py로 집계하고 별도 대사한다. DNS 복귀만으로 데이터 역이전은 되지 않는다.
