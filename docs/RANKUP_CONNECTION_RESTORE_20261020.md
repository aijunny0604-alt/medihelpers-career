## 느려진 원인과 실제 변경

2026-09-27 네임서버를 Cloudflare로 바꾼 이력과 10월 19일 복구 기록을 대조했다. 10월 19일에는 새 앱의 Workers Routes 두 개만 해제했으며 Cloudflare 프록시와 네임서버는 남아 있었다. 따라서 홈페이지는 랭크업으로 돌아왔지만 원래 접속 경로까지 복구된 상태는 아니었다.

동일 PC에서 각 경로를 3회씩 측정한 결과 Cloudflare 경유가 원본 직접 연결보다 약 1.2~1.5초 느렸다. 해당 환경의 Cloudflare trace는 `colo=LAX`, `loc=KR`였다. 이는 해당 측정의 경유 지점이며 모든 방문자가 같은 지점을 사용한다는 뜻은 아니다.

1. 사용자 승인 후 Cloudflare의 apex·www A 레코드 두 개만 프록시에서 DNS 전용으로 변경했다.
2. 다른 DNS 레코드는 변경 전후 비교로 유지 확인했다. 새 앱 Workers Route는 0개다.
3. 원본 두 네임서버의 웹·메일 응답과 apex/www TLS를 먼저 확인했다.
4. 사용자 후이즈 로그인 및 등록인 인증 후 기존 네임서버 두 개로 저장했다.
5. 후이즈 완료 화면, 공식 WHOIS 변경일·네임서버, 외부 DNS 및 공개 페이지를 재검증했다.

Cloudflare 계정·Zone·보존 중인 새 사이트 Worker·D1을 삭제하지 않았다. 원본 랭크업의 파일·회원 DB·비밀번호·결제 설정을 이번 작업에서 변경하지 않았다. 과거 시점의 전체 서버 백업을 덮어쓴 작업이 아니다.

## 이번 검증 범위

네임서버 저장 후 15개 공개 경로를 공개 주소와 원본으로 각각 GET하여 모두 HTTP 200을 확인했다. 페이지 제목·폼 action/method·회원 구분 radio·공고 상세 링크 비교가 일치했고 PHP 오류 표식은 없었다. 원본 TLS 검증도 통과했다.

- 홈과 본문, 회원 로그인, 회원 구분, 개인·병원 가입 약관
- 병원 채용 메인·목록·JK 상세, 인재 목록
- 게시판, 고객센터, 서비스 안내, 다이렉트 결제폼, 관리자 로그인 화면

apex/www의 HTTP는 HTTPS www 홈으로 301 이동하며, HTTPS는 200·인증서 검증 성공이다. 앞선 같은 정상화 작업에서 상세 경로와 query를 유지한 HTTPS 전환, 개인·병원 로그인 구분 전환, 신용카드·실시간계좌이체·무통장 3개 선택 동작도 확인했다.

**기존 실회원 계정 로그인·신규 가입 제출·공고 등록 제출·실카드 승인/취소/환불·실메일 송수신은 수행하지 않았다.** 검수 계정이 없으며 공개 폼 정상 응답을 거래 성공으로 표시하지 않는다. 새 사이트에서 이전에 수행한 합성 결제 검수와 이번 랭크업 검증은 별개다.

문서만 갱신하며 신규 앱 단위·런타임 전체 검사를 재실행한 것으로 집계하지 않는다. `npm run build` 통과, 변경 문서의 상대 링크 418개에 누락 없음, `git diff --check` 통과를 확인했다. 초기 빌드는 실행 환경의 `spawn EPERM`으로 실패해 허용된 권한에서 다시 실행했다. 시작 시 GitHub 기준 브랜치·Sites 소스·로컬은 `3719703a4af33e87f81e3e7eac5f8e9859c7cd75`로 같았다. 새 사이트 운영 배포와 Route 재연결은 하지 않는다.
