# 관리자·저장·백업 직접 점검 — 2026-09-12

공개 배포 353과 생성 Worker를 점검했다. 이번 변경은 검수 스크립트와 문서이며 제품 코드·테스트 로그인·권한 정책을 변경하지 않는다.

## 실제 사이트 확인

- 관리자 회원 기록, 결제 원장, DB 테이블 현황, 백업 기록을 직접 열어 확인했다. 현재 관리자는 조회 중심이며 수정·환불·수동 백업 실행 화면을 제공하지 않는다.
- 운영 백업 목록 36개, 최신 성공 시각은 **2026-09-12 00:00:23 KST**(2026-09-11 15:00:23 UTC).
- 최신 백업 199,248바이트를 메모리에서 읽어 SHA-256을 계산했다. 실행 기록 및 다운로드 응답 헤더의 체크섬과 모두 일치했다. 실제 개인정보가 포함된 백업 파일은 로컬에 저장하지 않았다.
- 운영 회원·공고·결제 데이터를 수정하거나 운영 DB 복원을 실행하지 않았다. API 점검용 로그인 세션은 종료했다.

## 격리 환경 시험

`npm run build` 후 `node scripts/runtime-admin-storage-audit.mjs`로 재현한다. 실제 생성 Worker와 메모리 SQLite, 모의 R2를 사용하며 운영 데이터는 사용하지 않는다.

**32개 검사 통과**: 역할별 접근, 관리자 쓰기 요청 405, 이력서 저장·재조회·관리자 조회, 일일 자동 백업, 같은 날 중복 실행 방지, 다운로드 권한·경로·내용·캐시 정책, SHA-256, 손상 파일 제거 및 재시도 복구를 확인했다.

백업의 38개 테이블을 별도 SQLite에 복원해 모든 테이블 건수, 저장한 이력서 내용, 외래키 무결성을 확인했다. 로그인 세션은 백업에서 제외됐다. 초기 스키마 준비 중 허용된 테이블 탐색·중복 열 메시지는 결과의 sqlErrors에 남는다. 요청 실패와 구분해야 한다.

**실제 D1 복원, 업로드 파일 복원, 대용량·동시 운영 부하 검증을 완료했다는 의미는 아니다.** 기존 자동 테스트 227개 등은 이전 검수 기록이며 이번 32개와 실행 시점을 구분한다.

## 발견한 미수정 사항

| 항목 | 근거와 영향 |
|---|---|
| 백업 파일 날짜 깨짐 | 실제 목록 API의 uploaded가 빈 객체로 전달되어 UI에 `[object Object]`가 표시된다. |
| 체크섬 상태 혼동 | 목록 조회가 R2 customMetadata를 요청하지 않아 모든 파일이 ‘확인 대기’로 표시된다. 최신 파일의 실제 체크섬은 검증에 성공했다. |
| 시간대 불명확 | 실행 시각을 UTC 문자열 그대로 표시하며 시간대 표기가 없어 한국 시각과 9시간 차이가 난다. |
| DB 총건수로 오해 가능 | 상담 수는 병원 직접 지원을 제외한 집계다. 화면 4건, 백업 6건을 확인했다. 프로필 건수는 계정 수, 거래 건수는 주문 수, 환불 건수는 환불 상태 주문 수를 대신 표시한다. 채용 건수도 종료 상태 일부를 제외한다. 모든 테이블의 실제 전체 행 수를 보여주는 DB 관리 도구는 아니다. |
| 초기 연결 상태 오해 | 백업 정보 로딩 중 일시적으로 ‘설정 필요’가 보인 뒤 ‘정상 연결’로 바뀐다. |
| 백업 목록 확장 한계 | 목록은 최대 100개, 실행 기록은 30개로 제한되며 목록 페이지 이동이 없다. 현재 36개에서는 한도 초과를 재현하지 않았다. |

## 운영 판단

저장·자동 백업·관리자 조회는 확인됐다. 관리자에서 수정·환불·수동 백업을 수행하는 운영 기능은 현재 제한되어 있다. 기존 권한 정책을 유지한 상태의 결과다.

DB JSON 백업은 업로드 이미지·서류 파일 자체를 복사하지 않는다. 실제 별도 D1로 복구하는 리허설과 업로드 파일의 보존·복원 절차를 검증해야 장애 복구 준비 완료로 판단할 수 있다. 위 표시 오류도 후속 수정이 필요하다.
