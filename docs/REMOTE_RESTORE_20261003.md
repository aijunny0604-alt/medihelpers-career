정식 도메인 전환 직전까지 진행하라는 사용자 요청에 따라 DNS와 운영 결제 설정은 변경하지 않았다. 기존 검수 DB를 덮어쓰지 않고 별도 D1에서 복원했다. 무료 계정에서 임시 DB 하나만 추가했으며 시험 후 삭제하고 미리보기 서버도 종료했다.

## 발견한 문제와 검증된 처리

1. D1 SQL export를 그대로 import하면 자식 테이블이 부모보다 먼저 나와 `no such table` 또는 외래키 오류가 발생했다. 전체 CREATE TABLE을 먼저 배치하고 부모 테이블의 데이터를 먼저 넣어 해결했다. 단순히 foreign_keys를 끄거나 defer만 넣는 것으로 해결됐다고 가정하지 않는다.
2. 1MiB BLOB 청크의 SQL 리터럴은 길이 제한 때문에 `statement too long`으로 거부됐다. 파일 메타데이터와 청크를 **매개변수 바인딩을 사용하는 파일별 원자적 batch**로 복원해 해결했다. 크기·SHA256·순서·메타데이터까지 대조했다.
3. 임시 복원 도구의 JavaScript base64 변환은 반복 시험에서 무료 Worker CPU 제한을 초과했다. 임시 도구에서 nodejs_compat의 Buffer 디코딩/비교로 바꿔 전체 재시험에 성공했다. 운영 Worker 설정이나 업로드 API는 변경하지 않았다. 운영 파일 처리 부하 검증은 별도다.

## 재실행 절차

1. 현재 원본과 장애 시점의 변경분을 먼저 내보내고 해시를 보관한다. 백업에 회원 정보가 있으므로 Git·공개 저장소에 넣지 않는다.
2. **비어 있는 격리 DB**를 만들고 대상 ID가 운영/검수 DB와 다른지 확인한다. 운영 DB를 DROP하거나 import 대상으로 지정하지 않는다.
3. 파일 BLOB이 없는 신뢰할 수 있는 D1 export는 다음 로컬 도구로 준비한다. 출력 파일은 기존 파일을 덮어쓰지 않는다.

   `python scripts/prepare-d1-restore.py <원본.sql> <새로운-복원용.sql>`

   도구는 스키마와 모든 행의 동등성, 무결성·외래키를 검사한 후 출력한다. 순환 참조나 100,000바이트 초과 SQL은 출력하지 않고 중단한다. Python -O는 금지한다. 일반적인 임의 SQL 변환기가 아니다.
4. 대형 BLOB이 있으면 위 도구만으로 복원이 완료되지 않는다. 로컬 SQLite에서 원본을 읽어 비파일 데이터와 upload_objects/upload_chunks를 분리하고, 파일 SHA256을 먼저 검증한 뒤 격리 DB에 파일별 prepared batch로 넣는다. uploaded_at과 metadata_json도 원본 그대로 넣는다. 시험용 복원 HTTP 엔드포인트는 운영에 배포하지 않는다.
5. 격리 DB를 다시 export하여 모든 테이블의 행·스키마와 파일 해시를 비교한다. 자동 정리/메일/PG 콜백 등 부수 효과를 실행하지 않는다.
6. 재수행 증거를 보존하고 격리 DB/임시 서버를 정리한다. 검증 전에는 서비스 바인딩이나 DNS를 바꾸지 않는다.

현재 파일 바인딩 복원 리허설 도구는 보호된 로컬 감사 폴더에 있으며, 일반 운영용 자동 복원 기능으로 제품에 공개하지 않았다. 자동 백업·보관 스케줄과 반복 실행 가능한 운영 복원 패키지는 별도 잔여 항목이다.
