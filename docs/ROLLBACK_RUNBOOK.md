# 랭크업 복구 실행서

작성일: 2026-09-24 · 실행 전 리허설 필요. 구 호스팅을 유지한다는 사용자 결정에 따른다.

## DNS 복구와 데이터 복구의 구분

도메인을 기존 서버로 되돌릴 수 있어도 신규 사이트에서 생성된 회원·공고·이력서·결제·환불·동의 변경은 자동으로 랭크업에 반영되지 않는다. 기존 DB는 전환 시점 상태이며, 신규 기록을 누락시킨 채 쓰기를 재개하지 않는다.

| 상황 | 복구 조건 |
|---|---|
| 신규 쓰기를 한 번도 열지 않았고 PG 후속 변경도 없음 | 백업/원장 확인 → 구 DNS 복구 → 캐시 확인 → 구 기능 검증 후 재개 |
| 가입·게시·수정·삭제·동의 변경 발생 | 양쪽 동결 → 신규 변경분 보존 → 역이전·대사 또는 해당 기능 보류 → 검증 후 재개 |
| 결제·입금·취소·권리 소진 발생 | 위 절차에 PG 원장 대사와 권리 재계산 추가. DNS 복구만으로 주문을 취소/재승인하지 않음 |

## 실행 순서

1. 장애 시각·현상·마지막 정상 시점·담당자를 기록한다. 새 사이트의 신규 쓰기와 주문 생성을 중지하고 구 사이트도 계속 동결한다.
2. 진행 중 결제의 승인·입금·취소 콜백을 무작정 차단하지 않는다. 검증된 수신/보관 경로를 유지하고 주문별 PG 상태를 조회한다. 수신 경로가 준비되지 않았다면 전환 자체를 시작하지 않는다.
3. 새 D1/R2와 로그·주문/권리 변경분을 백업하고 체크섬을 기록한다. 장애 원본을 덮어쓰지 않는다. 전환 전 T0 백업, 개방 T1, 동결 T2, 신규 마지막 처리 시각을 보관한다.
4. T0 이후 변경을 모두 추출한다. 구 사이트의 지연 PG 통보·관리 작업도 포함한다. 단순 updated_at 비교만 사용하지 않고 삭제표시/감사이력/권리 사용내역을 함께 확인한다.
5. 제한된 복원 환경에서 랭크업 DB+파일을 복구하고 신규 변경분 적용을 시험한다. 스키마·역이전 도구가 없으면 회원 데이터가 안전하게 합쳐졌다고 보고하지 않는다.
6. 개별 회원·권리·금액 대사가 끝나지 않은 기능은 닫아 둔다. 운영 책임자가 예외 목록과 처리 담당자를 승인한 경우에만 영향 없는 읽기 기능을 먼저 재개한다.
7. 실행 전 확보한 정확한 DNS 레코드로 복구한다. 신규 서비스도 구 DNS 캐시가 남는 동안 점검/읽기 상태를 유지한다. 모든 고객이 즉시 같은 서버를 본다고 가정하지 않는다.
8. 구 사이트 로그인·게시 소유권·잔여권리·HTTPS·메일·결제 리턴을 재검증하고 순차 재개한다. 고객 안내와 해결되지 않은 주문의 개별 처리 기록을 남긴다.
9. 새 환경과 백업은 정리 승인 전 보존한다. 기존 랭크업 호스팅 해지나 MID/키 폐기는 별도 결정 사항이다.

## 신규 변경분 장부

보호된 운영 저장소에서 작성하며 이 문서에는 실제 개인정보를 기입하지 않는다.

| 필드 | 기록 기준 |
|---|---|
| 사건 ID·출처·발생/처리시각 | 기존/신규 구분, UTC+표시 시간대 |
| 회원/객체 ID 매핑 | 구 회원번호 ↔ 새 account_id, 원본 게시글/이력서/파일 ID |
| 변경 종류 | 생성/수정/삭제/공개·연락처 동의/탈퇴/비밀번호 변경 |
| 결제 식별 | 출처별 주문번호, TID, MID, 승인·환불 상태/금액 |
| 권리 변화 | 공고 기간, 잔여 횟수, 이미 열람한 대상, 회수/복원 근거 |
| 적용 결과 | 미처리/반영/보류, 멱등키, 처리자, 검증자, 증거 |

비밀번호 해시는 신규→구 형식으로 변환 가능하다고 가정하지 않는다. 충돌한 계정은 검증된 재설정 경로로 처리하고 임시 공통 비밀번호를 발급하지 않는다. 공개 동의 철회·탈퇴·삭제는 이전 공개 상태로 되돌려 개인정보를 다시 노출시키지 않는다.

## 결제 복구 원칙

- 기존/신규 주문번호 공간과 출처를 구분한다. 동일 MID를 쓰더라도 구 주문을 신 주문으로 매칭하지 않는다.
- PG 승인 완료·앱 저장 실패는 금액을 다시 청구하지 않고 거래 조회 후 저장 복구 또는 검증된 취소 절차로 해결한다.
- PG 승인 미상은 `조사 중`으로 관리한다. 단순 실패 처리나 임의 성공 처리로 권리를 지급하지 않는다.
- 취소는 PG 결과 확인과 권리 회수·공고 노출 중지·환불 원장 기록을 한 작업으로 추적한다. 반복 통보는 중복 취소·중복 회수를 만들지 않아야 한다.
- 전환 직전 발급된 가상계좌의 늦은 입금, 승인 후 늦은 리턴, 진행 중 환불도 주문별 대사한다. 구 거래 취소 창구를 계속 유지한다.
- 이니시스 콜백 주소가 도메인 전환으로 새 서버에 도착할 수 있다. 구/신 주문을 구분해 처리하거나 검증된 전달 경로를 준비해야 하며 현재 완료로 간주하지 않는다.

## 리허설 합격 기준

신규 회원 1명, 기존 회원 수정·동의 철회, 게시글 생성/수정/삭제, 첨부 변경, 결제 완료/상태 미상/환불/권리 사용을 테스트 자료로 만든다. 동결→증분 보존→격리 역이전→PG 대사→구 기능 확인을 수행한다. 실데이터를 테스트에 공개하지 않는다.

재개까지 걸린 시간(RTO)과 누락 가능한 변경 구간(RPO)을 실측해서 기록한다. 거래·회원 변경 누락 0을 목표로 하되 검증 전 보장하지 않는다. 현재 일일 백업만으로 무손실 복구가 입증된 것은 아니다.

**현재 미완료:** 전체 쓰기/신규 주문 중지 장치, 완전한 증분/삭제 장부, 역이전 importer, 구/신 PG 리턴 분기, 운영 복원 리허설. 문서 작성 완료와 복구 가능성 검증 완료를 구분한다.
